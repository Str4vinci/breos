# 0.6.x projected optimization plan

## Decision

BREOS 0.6.0 is the projected-lifetime optimization and reproducibility
release. Time-of-use tariffs, explicit currency, and smart charging move to
0.7.0. The tariff architecture remains accepted; only its release target
changes.

The 0.6.0 scope is:

1. opt-in repeated-TMY projected optimization using lifetime grid
   independence and NPV;
2. yearly battery state carry, actual replacements, and annual financial
   valuation for every candidate;
3. detailed fixed-design source tables for energy, degradation, replacements,
   LCOE, emissions, and discounted cashflows;
4. reproducible historical-weather Monte Carlo with explicit demand
   distribution, weather-year pool, seed, worker count, yearly trajectories,
   and input/output hashes;
5. a generic projected-optimization example plus a versioned Article 1
   reproduction case as validation evidence; and
6. removals already deprecated and announced for 0.6.0.

Annual three-objective optimization remains the default. Projected mode is
explicit and bi-objective. ZEB remains a diagnostic unless the user enables it
as a feasibility constraint.

## Architecture boundary

Projected workflows must reuse the production PV, inverter, battery,
degradation, replacement, economics, emissions, and load-alignment components.
Do not port the research repository's parallel runner, battery engine,
economics engine, or plotting layer.

The public result contract must be sufficient for users to create their own
plots without requiring BREOS to provide manuscript-specific visualization:

- headline projected metrics;
- one row per project year for energy and degradation state;
- one row per project year for discounted financial and emissions values;
- one row per Monte Carlo trajectory for endpoint distributions;
- optional one row per trajectory-year for cost envelopes; and
- provenance containing the resolved configuration, software/source version,
  random seed, input hashes, and output hashes.

Generated scientific results belong in ignored `results/` directories. Small
configs, commands, regression references, and reproduction reports are
version-controlled.

## Article validation boundary

Article-specific configuration is useful evidence that the general feature
works. It must not change production defaults or create an Article-only
simulation path. Licensed load profiles and large historical-weather inputs
remain external and are identified by hash.

BREOS does not need to own the paper's plotting code. Before claiming full
study reproducibility, however, versioned commands or provenance-bound source
tables must cover the orientation grid, projected Pareto front,
representative cost/degradation paths, TMY-versus-historical comparison,
Monte Carlo distributions, load-profile sensitivity, degradation-model
sensitivity, LCOE, and emissions.

## Release gate

0.6.0 is ready when:

- projected fixed candidates and a small optimization pass on supported
  Python versions;
- lifetime aggregation, state carry, replacements, ZEB semantics, detailed
  outputs, Monte Carlo distributions, and provenance have automated coverage;
- the final field-v1, field-v2, and laboratory Article configurations have
  been run from a clean release candidate by the study author;
- corrected-model differences are documented rather than hidden by tolerances;
- the Article module coefficient, final-hour weather interpolation, and
  low-light clear-sky reconstruction fixes are included before the final
  scientific run;
- the final corrected C1-C4 values replace the deliberately disabled
  transitional numerical regression baseline;
- the manuscript's numerical claims are updated from those final outputs;
- standard tests, Ruff, strict documentation, build, and installed-artifact
  verification pass; and
- no tariff or smart-charging branch is merged into the 0.6 release solely to
  preserve the earlier roadmap.

Creating a tag, publishing artifacts, or releasing to PyPI remains a separate
explicit action after these gates pass.
