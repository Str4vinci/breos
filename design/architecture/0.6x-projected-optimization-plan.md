# 0.6.x projected optimization plan

## Decision

BREOS 0.6.0 is the projected-lifetime optimization and reproducibility
release. Time-of-use tariffs, explicit currency, and smart charging move to
0.7.0. The tariff architecture remains accepted; only its release target
changes.

The 0.6.0 scope is:

1. repeated-TMY projected optimization using lifetime grid independence and
   NPV by default;
2. yearly battery state carry, actual replacements, and annual financial
   valuation for every candidate;
3. detailed fixed-design source tables for energy, degradation, replacements,
   LCOE, emissions, and discounted cashflows;
4. reproducible historical-weather Monte Carlo with explicit demand
   distribution, weather-year pool, seed, worker count, yearly trajectories,
   and input/output hashes;
5. a generic projected-optimization example plus a versioned reproduction case
   for the forthcoming publication as validation evidence;
6. removals already deprecated and announced for 0.6.0; and
7. a summary-only simulation path and a private optional Numba daily dispatch
   kernel, selectable for Monte Carlo only, that make the publication study's
   Monte Carlo tractable without changing its scientific output.

Projected bi-objective optimization is the default. Annual three-objective
optimization remains available through `objective_basis = "steady_state"` for
lower-cost screening. ZEB remains a diagnostic in projected mode unless the
user enables it as a feasibility constraint.

## Architecture boundary

Projected workflows must reuse the production PV, inverter, battery,
degradation, replacement, economics, emissions, and load-alignment components.
Do not port the research repository's parallel runner, battery engine,
economics engine, or plotting layer.

Accelerating the existing engine is inside this boundary. A summary-only
result path and a private daily dispatch kernel speed up the current BREOS
dispatch and ledger; they do not import the research repository's battery
engine, Monte Carlo runner, economics engine, or plotting layer. Only the
day-boundary *structure* is adopted from that repository. Every dispatch
semantic, ledger field, and state transition stays BREOS's own.

The public result contract must be sufficient for users to create their own
plots without requiring BREOS to provide manuscript-specific visualization:

- headline projected metrics;
- one row per project year for energy and degradation state;
- one row per project year for discounted financial and emissions values;
- one row per Monte Carlo trajectory for endpoint distributions;
- optional one row per trajectory-year for cost envelopes; and
- provenance containing the resolved configuration, software/source version,
  random seed, input hashes, and output hashes.

Generated scientific results belong in ignored `results/` directories. Small
configs, commands, regression references, and reproduction reports are
version-controlled as repository-only material. They are not part of the
installed BREOS package or its public API.

## Monte Carlo execution performance

### Measured starting point

The forthcoming publication's headline analysis is 10,000 trajectories over
20 years at 15-minute resolution for cases C1-C5. Measured on an AMD Ryzen AI
9 365 (10 physical, 20 logical cores):

- C2 takes about 3.5 hours of wall time on eight workers.
- Marginal single-core cost per trajectory is C1 6.28 s, C2 10.33 s, C3
  9.04 s, C4 10.10 s, C5 6.54 s.

Those marginal costs imply about 14.5 hours for all five cases. That total is
extrapolated, not measured, and must not be quoted as measured until every
case has completed.

Profiling two C2 trajectories under cProfile:

- Essentially all trajectory time is inside
  `breos.battery.simulate_energy_balance`.
- 1,401,600 calls to `_dispatch_dc_step`, one per 15-minute step.
- 1,487,529 `pandas.DatetimeIndex.__getitem__` calls, about 24% of trajectory
  time, caused by `step_time = rng[i]` at the top of the per-step loop.
- 2,190,992 calls to `breos.inverter.calculate_dc_ac_power`.
- PV and weather are already cached per weather year by
  `breos.montecarlo._precompute_year_caches`, once per study rather than per
  trajectory.

PV is not the bottleneck. The Python per-timestep dispatch loop is.

`breos.montecarlo` additionally builds a full 35,040-row timestep DataFrame
for every simulated year, reduces it to annual totals and final state, and
discards it. Monte Carlo needs those aggregates; it does not need the frame.

### The two changes

**A summary-only simulation path.** It runs the current Python physics and
returns annual energy totals, annual grid independence, final degradation
state, replacements and costs, carried battery energy, carried PV-origin
energy, and temperature diagnostics, without building the per-timestep frame.
Monte Carlo routes through it.

**A private daily dispatch kernel** in `breos._numba_dispatch`, compiled with
Numba, reproducing the current BREOS dispatch exactly: `_dispatch_dc_step`,
`_apply_capacity_window`, the finite PVWatts inverter conversion and its
inverse, charge and discharge caps, PV-origin energy accounting, every
loss-ledger field, and carried energy across years.

The summary-only path lands first. It is the refactor that makes the kernel
swap safe and independently testable, and it is the only place the two
backends can be compared field by field.

### Degradation stays in Python

The compiled kernel runs one day at fixed state of health and fixed
resistance. The surrounding structure is:

```
Python year loop
  Python day loop
    compiled dispatch kernel for 24 or 96 timesteps
  Python rainflow counting
  Python calendar and cycle degradation
  Python resistance update
  Python replacement decision
```

Every scientifically sensitive state transition stays in authoritative
Python. Do not compile rainflow counting, degradation, resistance growth,
replacement, or day-boundary state.

### Deprecation conflict

The 0.5.x deprecation notice scheduled both `breos.numba_kernels` and the
`breos[fast]` extra for removal in 0.6.0. That is resolved as:

- `breos.numba_kernels` is removed as announced. It is an approximate
  standalone screening engine with no production caller, and it duplicates
  degradation and replacement science.
- `breos[fast]` is retained and undeprecated. It becomes the supported way to
  install the optional accelerator.
- The new kernel is private: `breos._numba_dispatch`. It is not public API and
  carries no compatibility guarantee.

### Backend selection

The backend is a Monte Carlo setting only:

```toml
[montecarlo]
execution_backend = "numba"
```

- `"python"` is the default and the reference path.
- `"numba"` is an explicit, optional accelerated path.
- There is no `"auto"` mode.
- Selecting `"numba"` without the extra installed fails before any trajectory
  starts, not partway through a long study.
- Provenance for Monte Carlo and the publication study records every run, not
  only benchmarks:
  - the resolved `execution_backend`;
  - whether the Numba JIT cache was warm or cold for that run;
  - the installed Numba and llvmlite versions.

  The bit-identity claim below is scoped to a fixed toolchain, so it is
  unverifiable after the fact without the compiler versions, and a cold-cache
  run carries LLVM compile time that a warm one does not. Both fields must
  describe what actually happened, not what was intended.

BREOS must remain fully functional without Numba through the Python reference
path. Extending the backend to `App` and to projected optimization is 0.7.x
work; see
[0.7x-tariffs-and-smart-charging-plan.md](0.7x-tariffs-and-smart-charging-plan.md).
This release stays on the measured bottleneck.

### Numerical parity

Kernel constraints: `@njit(cache=True, fastmath=False)`, no `parallel=True`,
no `prange`, and unchanged operation order relative to the Python path.

One of those constraints is not obvious and is load-bearing. CPython evaluates
`zeta ** 2` in the PVWatts part-load polynomial as a libm `pow` call, and for
some inputs glibc's `pow` differs by one ULP from the correctly rounded square.
LLVM rewrites a constant-exponent `pow` into `x * x` and picks up that ULP, so
the kernel keeps the exponent opaque until run time (`math.pow(zeta, pow_two)`,
with `pow_two` passed in) to force the same libm call the reference makes.
Simplifying that back to `zeta ** 2` is algebraically identical and breaks bit
identity. `test_zeta_squared_must_use_libm_pow_not_the_folded_square` pins an
input where the two spellings actually disagree; without it the change is
silent.

The general rule this illustrates: a rewrite that is algebraically equivalent
but changes which machine operation is issued is a defect here, not a
simplification.

The target is bit-identical output between the two backends on the same
machine, Python version, NumPy version, Numba version, and LLVM toolchain.
BREOS does not promise cross-platform bit identity: even with fast-math
disabled, compiler and CPU differences can move the last bit.

Acceptance:

- Exact comparison first.
- Event fields (replacement years and counts), integers, and booleans: exact.
- Energy-ledger conservation: a strict invariant, not a tolerance.
- If exact comparison fails, explain the operation that causes it and use a
  field-specific ULP bound. A global `atol=1e-9` or a global relative
  tolerance hides the reason and must not be used.
- Projected grid independence and NPV: manuscript rounding unchanged.

Parity coverage must include PV-origin battery inventory, carried battery
energy across years, capacity-window losses, replacement energy removed and
added, separate direct-PV and battery inverter losses, all cumulative
degradation components, C1-C5 fixed-candidate metrics, serial and
multiprocessing Monte Carlo, identical weather-year and load-scale draws,
exact replacement years and counts, and the weather-driven indoor-temperature
branch.

The indoor-temperature model is a Series-to-Series transform applied before the
loop, so the kernel cannot distinguish a remapped series from raw weather or
from a pinned constant: there is no indoor-specific code path to cover. What
does need covering is the temperature *range*, because `lfp_capacity_factor`
branches at 25 C and at 0 C and saturates at 0.5, and `compute_cell_temperature`
runs every step. Parity is therefore checked at the pinned 25 C the manuscript
uses, on both branch boundaries, below zero, at the derating floor, above the
indoor ceiling, on the indoor model's own clamp bounds, and on the model's
output end to end.

Benchmarks are recorded after warm-up. `cache=True` writes compiled artifacts
to `__pycache__` on first use, so a cold-cache measurement includes LLVM
compile time and understates the gain. The cache also invalidates on a Numba
upgrade and on any kernel source change, so a run that was warm yesterday can
be cold today. The provenance fields above are therefore detected per run
rather than assumed.

## Publication-study validation boundary

Configuration for the publication study is useful evidence that the general
feature works. It must not change production defaults or create a simulation
path dedicated to the publication. Licensed load profiles and large
historical-weather inputs remain external and are identified by hash.

BREOS does not need to own the paper's plotting code. Before claiming full
study reproducibility, however, versioned commands or provenance-bound source
tables must cover the orientation grid, projected Pareto front,
representative cost/degradation paths, TMY-versus-historical comparison,
Monte Carlo distributions, load-profile sensitivity, degradation-model
sensitivity, LCOE, and emissions.

## Release gate

0.6.0 is ready when:

- projected fixed candidates and a small optimization pass on supported
  Python versions;
- lifetime aggregation, state carry, replacements, ZEB semantics, detailed
  outputs, Monte Carlo distributions, and provenance have automated coverage;
- the final field-v1, field-v2, and laboratory configurations for the
  publication study have been run from a clean release candidate by the study
  author;
- corrected-model differences are documented rather than hidden by tolerances;
- the publication study's module coefficient, final-hour weather interpolation,
  and low-light clear-sky reconstruction fixes are included before the final
  scientific run;
- the final corrected C1-C4 values replace the deliberately disabled
  transitional numerical regression baseline;
- the manuscript's numerical claims are updated from those final outputs;
- the summary-only path reproduces the full simulator's annual totals,
  degradation state, carried energy, and replacement events;
- the Numba backend is bit-identical to the Python backend on the release
  machine, with any surviving difference explained and bounded per field
  rather than by a global tolerance;
- a seeded C1-C5 comparison run agrees between backends, and warm one-worker
  and eight-worker benchmarks record the measured speedup;
- standard tests, Ruff, strict documentation, build, and installed-artifact
  verification pass; and
- no tariff or smart-charging branch is merged into the 0.6 release solely to
  preserve the earlier roadmap.

Creating a tag, publishing artifacts, or releasing to PyPI remains a separate
explicit action after these gates pass.
