## 1. Benchmarks (done) and the parity work they unblocked

The live Article run finished on 2026-08-24. C1 and C2 are complete at 10,000
trajectories each; C3-C5 were never part of that bundle. See
`article1-montecarlo-v1-partial` in the maintainer notes — it must not be cited
as a full C1-C5 reference.

Measured on this machine, 20 modules' worth of logical CPUs, 20-year
trajectories, setup timed separately because the year caches cost the same on
both backends:

| Workers | Python | Numba | Ratio |
|---|---|---|---|
| 1 | 5.85 s/trajectory | 0.60 s/trajectory | ~9.8x |
| 10 | 0.83 s/trajectory | 0.085 s/trajectory | ~9.8x |

**Read this as an order of acceleration, roughly 9x, not as a figure to
reproduce.** It is one machine and one configuration; the evidence covers one
and ten workers, and says nothing about any other machine. What matters is the
shape: the ratio is flat between one worker and ten, so
acceleration and pooling compose rather than compete. Both backends lose the
same fraction to pooling overhead. Quote the order, not the digits.

The numba column is also slightly pessimistic, because every worker recompiles
the dispatch kernel — see the cache defect in section 2.

Still open, and no longer blocked:

- **Full-scale C2 against the complete bundle.** 25 of 10,000 trajectories are
  verified exactly. Because the per-run seed is `seed + run_index` and
  independent of `n_runs`, that is an exact check on a subset rather than a
  sampled one — but a full accelerated C2 would close validation step 7 outright.
- **C1 the same way.** C1 has no battery and takes a different dispatch branch
  from C2. The bundle's provenance records `execution: null`, confirming it came
  from pristine `ac5c778` on the Python path, which makes it the correct
  bit-identity reference for an accelerated rerun.

## 2. Verification debt in the JIT-cache observation

Reading Numba's dispatcher hit and miss counters is the right call — a `.nbi`
file on disk is not evidence of a hit, since Numba can reject a stale index.
The rework is sound and parity survives it. Three things still need attention.

- **A provenance failure can now abort a study.** `_dispatch_day_numba` raises
  `RuntimeError` when it cannot classify the cache outcome, and
  `_run_trajectory_index` raises when a trajectory reports nothing. Both sit on
  the path of a run that may already be hours old. Bookkeeping about a run
  should not be able to destroy the run. Prefer recording `"unknown"` and
  letting the study finish; a provenance field that says it could not tell is
  more useful than no results at all. If the raise stays, it needs a comment
  explaining why aborting beats degrading.
- **`kernel.stats.cache_hits` and `kernel.signatures` are Numba internals** with
  no stability guarantee across releases. Confirm the regression tests fail
  loudly rather than silently mis-reporting if a Numba upgrade changes those
  attributes, and record the version scope next to the bit-identity scope
  already noted in the plan.
- **Multiprocessing aggregation is untested at scale.** The unit tests cover
  mixed worker observations, but no run with `n_procs > 1` and a genuinely cold
  cache has been observed end to end.

### `cache=True` is inert on `_dispatch_day_kernel` (confirmed 2026-08-24)

The bullet above cannot be satisfied as written, because the kernel never
reports `warm`. `cache=True` has no effect on `_dispatch_day_kernel`, and the
cause is structural rather than incidental.

All four kernels are defined inside `_build_kernel()`. The three leaf helpers
have no free variables, so they cache correctly. `_dispatch_day_kernel` closes
over the other three — `co_freevars` is `('_dc_ac', '_dc_for_ac',
'_lfp_capacity_factor')`, each cell holding a `CPUDispatcher` — and Numba's
index key for a closure includes the cell contents, which are not stable across
processes. The key therefore never matches a previous process's entry.

Evidence, three independent lines:

1. `NUMBA_DEBUG_CACHE=1` over two subprocesses sharing one `NUMBA_CACHE_DIR`:
   the three helpers log `index loaded` **and** `data loaded`; the dispatch
   kernel logs `index loaded` then `data saved ... .2.nbc`. It reloads the
   index, fails to match, recompiles, and appends a new entry.
2. Minimal reproduction, outside this codebase. Identical two-function code,
   `cache=True` on both. Defined at module level: miss, then hit. Defined inside
   a factory: miss, then miss.
3. The cache directory grows without bound. Four sequential single-run processes
   leave `.1.nbc` through `.4.nbc` for the dispatch kernel, about 200 KB per
   process, never reused.

Three consequences:

- Every process recompiles the dispatch kernel, roughly 0.6 s. A pooled study
  pays it per worker, once — negligible against a study of any size. A single
  App run pays it in full, every time, which is exactly the first-run cost
  section 3a has to answer.
- `NUMBA_CACHE_DIR` grows monotonically for the lifetime of the install.
- `observed_jit_cache_state` will record `cold` forever, so the provenance field
  reports a constant rather than an observation. This makes the RuntimeError in
  the first bullet worse, not better: the classification it defends is
  meaningless for this kernel.

**Fix:** hoist the four kernels to module level so the dispatch kernel resolves
its helpers as globals rather than closure cells. Numba keys globals by
qualified name, which is stable — that is what makes case 2 above cache. The
change is mechanical, but it touches the parity-verified hot path, so the full
parity chain has to be re-run afterwards.

## 3. Release-blocking and not started

- **`breos.numba_kernels` is still present.** The 0.5.1 notice scheduled it for
  removal in 0.6.0, `docs/deprecations.md` says it "is removed in 0.6.0", and
  `CHANGELOG.md` already states the removal "proceeds as announced". The module
  is still on disk, so the changelog currently describes work that has not
  happened. Remove the module and `tests/test_numba_kernels.py`, and check
  `breos/__init__.py` and `tests/test_deprecations.py` for references.
  This is independent of the new kernel: the new one is private
  (`breos._numba_dispatch`) and selected through configuration, never by import.
- **Configuration reference.** `docs/getting-started/configuration.md` documents
  the `[montecarlo]` section but never mentions `execution_backend`.
  `docs/deprecations.md` and `docs/getting-started/troubleshooting.md` already
  do, so the config reference is the gap. Document the default, the `breos[fast]`
  requirement, the fail-before-start behaviour, and that `"python"` is the
  numerical reference.
- **`--execution-backend` is undocumented** in the CLI prose, for both
  `breos montecarlo` and the Article reproduction tool.

## 3a. App acceleration (decided into 0.6.0)

The kernel already runs under the detailed-output path — that is what the
628-field pristine-vs-Numba timestep comparison exercises — so this is
plumbing and evidence, not new numerics. The work:

- **Route App through the backend selector.** Same `execution_backend` choice
  Monte Carlo uses, same fallback when numba is absent. App must not acquire a
  second, divergent way of deciding whether the kernel runs.
- **Extend provenance to record the backend.** App writes provenance that Monte
  Carlo does not; a run accelerated by a compiled kernel has to say so, with the
  numba and llvmlite versions, or the bit-identity claim is unverifiable after
  the fact.
- **Parity on App's own output contract.** The timestep evidence covers the
  physics; it does not cover App's assembled outputs. Add a full-output App
  comparison, Python vs Numba, over a real config — the same harness style as
  `tools/parity/compare.py`.
- **Measure it.** The 0.6.0 claim for App should be a measured number on the
  same machine as the Monte Carlo benchmarks, not an extrapolation from the
  trajectory speedup. App spends its time differently.
- **First-run compile cost is visible here in a way it is not in Monte Carlo.**
  A 10,000-run study amortises a cold JIT compile; a single App run does not.
  Decide what the user sees — a warmed cache, a message, or a documented
  first-run pause.

## 4. Shipping hygiene

- **`tools/parity/` must be committed.** `tests/test_numba_dispatch_parity.py`
  inserts it on `sys.path` and imports `harness`, so the test suite breaks if
  the directory is left untracked. Decide deliberately whether it ships as a
  supported harness or is marked as a development-only tool, but it cannot
  simply be omitted.
- **Pin or scope ruff.** `pyproject.toml` allows `ruff>=0.15`; 0.16.4 reformats
  Python code blocks inside Markdown, so a bare `ruff format .` rewrites
  `README.md`, `docs/index.md`, two files under `docs/getting-started/`, and two
  design documents. It does this on pristine `ac5c778` too, so it is
  pre-existing rather than caused by this branch, but it will keep producing
  unrelated diffs until it is pinned or the format target is scoped.
- **Commit the branch.** It is one coherent piece of work but should not be a
  single commit: the buffer-matrix refactor, the summary path, the kernel, the
  `remap_datetime_index_years` vectorisation, the diagnostics, and the backend
  plumbing are separately reviewable and separately revertable.

## 5. Decisions needed

- ~~Does App acceleration come into 0.6.0 or stay in 0.7.x?~~ **Decided
  2026-08-24: App acceleration ships in 0.6.0.** It is the user-facing win, and
  the kernel is not Monte Carlo-specific, so the extension is mostly plumbing.
  What the decision buys is listed as work in section 3a, because the reason it
  was a question stands: App carries provenance and output contracts Monte Carlo
  does not, and those have to be honoured rather than inherited.
- **Does `remap_datetime_index_years` deserve wider treatment?** It is now a
  public function with two paths — vectorised for tz-naive and fixed-offset
  indices, element-wise for zones that can have transitions. That split is worth
  stating in the public documentation, because the fast path is bit-exact only
  where it applies and the fallback is the authority.

## 6. Accepted limitations, to state rather than close

- Bit identity is scoped to one toolchain (numba 0.66.0, llvmlite 0.48.0, and
  the platform libm). Cross-platform bit identity is not promised. Provenance
  records the versions for exactly this reason.
- Chemistry variation is not covered by the parity tests, and deliberately so:
  the kernel takes no chemistry argument, and `battery_type` feeds only the
  Python-side degradation and resistance models. `lfp_capacity_factor` is
  unconditionally LFP on the reference path too. This is a modelling question,
  not a parity gap.
- The compiled dispatch is now roughly 2% of trajectory time. Further gains have
  to come from the day-close degradation work — rainflow counting and the
  aging models — which the plan deliberately keeps in Python.
